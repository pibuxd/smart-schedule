# CLAUDE.md

Grafikomat: web app for building work schedules for shift-based venues (bakeries, cafés, restaurants, hotels).
Scope and requirements: `docs/spec.md`. Technical plan, data model, endpoints, stages: `docs/plan.md`.

## Working rules

- Talk to Piotr in Polish. Code, identifiers and commit messages in English. UI text in Polish.
- One stage = one thread = one pull request. Run tests and linters before opening a PR.
- When a decision changes, update `docs/spec.md` (and `docs/plan.md`) first, then the code.
- Do not add technology outside the stack below without asking.
- Secrets only in environment variables (`.env` is git-ignored, `.env.example` is committed).
- If something is unclear, make a reasonable assumption, write it in the PR description, and continue.
- Keep this file current when commands or conventions change.

## Stack

- Backend (`backend/`): Python 3.13, Django + Django Ninja (OpenAPI), PostgreSQL 16, Django sessions, dependencies managed with `uv`.
  `pypdf` reads text from PDF lists of people (`apps/tenancy/people_list.py`); XLSX and CSV use the standard library.
- Background jobs: Procrastinate on Postgres (no Redis). Worker = `manage.py procrastinate worker`, same code as the API.
  Save data and defer the job in one `transaction.atomic()` block.
- Scheduling engine (`backend/engine/`): pure Python, must not import Django. OR-Tools CP-SAT runs only in the worker.
- Frontend (`frontend/`): TypeScript, React + Vite SPA, TanStack Router (file routes in `src/routes`) + TanStack Query,
  Tailwind CSS v4 (+ shadcn/ui from stage 6), React Hook Form + Zod, dnd-kit. API client generated by orval.
- Docker Compose: `db`, `api` (gunicorn), `worker`, `caddy` (serves the SPA, proxies `/api`, serves Django static files).
- LLM: OpenRouter via the `openai` Python SDK (default model `deepseek/deepseek-v4.1-flash`), key only from
  `OPENROUTER_API_KEY`, model from `OPENROUTER_MODEL`, thinking depth from `OPENROUTER_EFFORT` (default `low`; every tool
  round is a full call, so keep it low). Only when that key is empty: Claude via the Anthropic Python SDK
  (`ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `ANTHROPIC_EFFORT`). The key picks the service; an OpenRouter failure never
  switches to Claude by itself. Answer schemas come from the Pydantic models in `llm.py`.

## Commands

Everything at once (http://localhost:8080):

```bash
cp .env.example .env        # once
docker compose up --build
```

Backend outside Docker (needs Postgres, e.g. `docker compose up -d db`):

```bash
cd backend
uv sync
uv run python manage.py migrate
uv run python manage.py seed_demo [--reset]              # demo data: 4 bakeries + a separate café
uv run python manage.py seed_test_data [--reset|--delete]  # 3 test companies for manual testing (+48 510/520/530…)
# log in: POST /api/auth/request-code, the code is printed by runserver ("SMS to +48…")
DJANGO_DEBUG=1 uv run python manage.py runserver          # API on :8000
DJANGO_DEBUG=1 uv run python manage.py procrastinate worker   # all queues (in Docker: `worker` + `solver`)
uv run python manage.py assistant_misses --days 30 > misses.csv   # what the assistant could not turn into settings
uv run python manage.py assistant_costs --month 2026-11 --by person > costs.csv   # what the assistant cost (also --by location|company)
uv run python manage.py generate_schedule --company 6a1e0000-0000-4000-8000-000000000001  # try the generator now
uv run pytest                                             # tests (need Postgres)
DJANGO_DEBUG=1 uv run pytest tests/engine                 # engine tests only, no database needed
uv run ruff check . && uv run ruff format --check .       # lint
uv run python manage.py makemigrations --check --dry-run
```

Frontend (dev server on :5173 proxies `/api` to :8000):

```bash
cd frontend
npm install
npm run dev
npm run lint && npm run typecheck && npm test && npm run build
```

After changing the API, regenerate the schema and the client (CI fails if they are stale):

```bash
cd backend && uv run python manage.py export_openapi_schema --api config.api.api --indent 2 --output ../frontend/openapi.json
cd ../frontend && npm run api:generate
```

Deployment on a single VPS (`docs/deploy.md`): `deploy/setup-server.sh` (first run), `deploy/update.sh` (new version),
`deploy/backup.sh` (daily dump from cron), `deploy/auto-update.sh` (cron, every 5 minutes: deploys new commits on `main`,
so everything merged to `main` goes live by itself). The server uses `.env` made from `.env.production.example`, which adds
`docker-compose.prod.yml` (ports 80/443, database not exposed). Never commit server addresses, passwords or keys.

## Conventions

- API lives under `/api`; every endpoint is in a router of its app (`apps/<app>/api.py`) and added in `config/api.py`.
  OpenAPI operation id = view function name, so name views as the frontend hook should read (`health` → `useHealth`).
- Tenant isolation (from stage 2): every company-owned model inherits `apps.tenancy.base.CompanyOwnedModel`
  (UUID id, `company_id`, `company_from` copies the company from a parent; cross-company links are rejected on save
  and on m2m add). API code starts with `ctx = tenant_context(request, company_id)` and reads only via
  `ctx.qs(Model)` / `ctx.get(Model, ...)` (404 for other companies). `tests/test_tenant_guard.py` fails on plain
  `Model.objects` in `api.py` unless the line has `# tenant-ok: <reason>`. Each new endpoint gets a cross-company test.
- Auth: every endpoint needs a session (`auth=django_auth` is the API default, CSRF included); only `health`,
  `auth/*` and `GET /me` use `auth=None`. Endpoints addressed by an object id start with
  `ctx, obj = context_for(request, Model, id)`. Every endpoint that changes company data calls
  `ctx.require_writable()` (402 when the company's access has expired) and the right `ctx.require_manager*()`.
- Errors are `HttpError(status, "<Polish sentence for the user>")` → `{"detail": ...}` (`apps.core.schemas.ErrorOut`).
  When a failure must leave a trace (attempt counters), raise after the `transaction.atomic()` block, not inside.
- Login codes: `apps/accounts/login.py`; SMS goes through `settings.SMS_BACKEND` (console by default; tests use
  the `sms_outbox` fixture). Rate limits need the client IP: `apps.core.http.client_ip` + `DJANGO_NUM_PROXIES`.
- Inviting many people (`apps/tenancy/people_list.py` reads a pasted list or a CSV/XLSX/PDF file without a model;
  `invitations.check_people` / `invite_people` decide; `Invitation.positions` are given on acceptance). The manager's
  assistant reads a file too (`assistant-commands/file`, `AssistantCommand.attachment`, text dropped once read) and
  proposes `invites`; phone numbers reach the model only as `[TEL1]` marks (`people_list.PhoneMask`), and a person who
  cannot be invited is left out with a note instead of blocking the plan.
- Users: `apps.accounts.User`, login field `phone_e164` (normalized with `normalize_phone`, +48 only). App users
  have no password; only the Django admin superuser has one.
  `User.bank_account` (optional plain text as written, any bank; `normalize_bank_account` only tidies spaces) belongs
  to the person like the name: set in "Twoje dane" (`PATCH /me`) or by a manager with the name's rule
  (`staffing.api._changed_account`, `EmployeeOut.other_company`; the person gets `bank_account_set`). Only the person
  and the managers of their locations see it; never put it in the assistant's tool results (`tools.DROPPED_KEYS`).
- A person can work in several locations of a company: `EmployeeProfile.home_location` (main) plus
  `extra_locations`. "People of a location" is `works_in_q(location)` / `profile.works_in(location)`, never
  `home_location=` alone; in the engine `Employee.works_in`. Availability and monthly hours are per person.
- People may hold several positions (`EmployeeProfile.positions`). An employee's wish about one of them ("nie chcę
  być sprzedawcą w tym tygodniu", reading type `stanowisko`) is `engine.problem.Request(type=POSITION, positions=…)`,
  soft like `shift_type`; with one position the assistant explains instead of saving it (`services._position_question`).
- Schedules arranged but not published (period status `draft`) lock their days in "Kiedy mogę" (`unpublished`) and
  are named in "Mój grafik" (`preparing`); employees only ever see published shifts.
- Rules a location can use come only from `engine/rules_catalog.py`; `RuleSetting.rule_code` must be in it.
  Each catalog rule needs a `rule_<code>` method in `engine/validator.py` and a `_rule_<code>` method in
  `engine/solver.py` (hard: a constraint; soft: a penalty matching the validator's degree), checked by a test.
- Engine: the Django layer builds an `engine.problem.Problem`; `engine.validator.validate` checks a schedule and
  `engine.scoring.score` turns the report into the three numbers. Durations always in UTC, dates in local time.
  `engine.solver.solve` (CP-SAT, worker only) builds a schedule; `apps/scheduling/problem_builder.py` reads the
  database into a `Problem`, `apps/scheduling/generation.py` queues, runs and saves generations. A solver result
  is saved only if the validator finds no hard violation.
  Violation messages are Polish sentences for the manager.
- Background tasks live in `apps/<app>/tasks.py` (auto-discovered). Solver jobs go to queue `solver`, the rest to `default`.
- Do not edit generated files: `frontend/src/api/generated/**`, `frontend/src/routeTree.gen.ts`.
- Frontend calls the API only through the generated hooks; `src/api/http.ts` adds the session cookie and CSRF token.
- Every screen has an empty, loading and error state with plain-language Polish text.
- Keep screens light on text: one short sentence at most under a heading. Longer explanations go in `Section`'s
  `description` (hidden behind the "i" button; add `alwaysExplain` when the text states a consequence); rarely needed
  lists use `<Section collapsible>` (`status` = a few words at the end of the folded heading). Every fold uses
  `components/ui/disclosure.tsx` (chevron that turns, tint on hover), never a bare `<details>`.
- UI copy follows the plain-language rules in `docs/plan.md` 15a point 10: short sentences, "ty" form, active verbs, buttons as
  commands that say what happens ("Wyślij kierownikowi"), one word per concept (keep "dyspozycje", "kierownik", "lokal").
- Visual tokens live in `frontend/src/styles/tokens.css` (Tailwind `@theme`; default colours, font sizes, radii and
  shadows are switched off, so only token classes exist: `bg-paper`, `text-ink`, `text-accent`, `rounded-md`, `text-lg`…).
  Control sizes: `min-h-(--touch)` (44 px, 36 px with a mouse) and `min-h-(--touch-main)` (48 px / 40 px). Body text is 16 px;
  spacing is in `rem`, so it follows the body size. No purple gradients, glass, emoji icons.
  Availability states always use colour + icon + pattern (`.avail-<state>` + `StateIcon`).
- Frontend layout: screens in `src/features/<area>/`, shadcn/ui-style building blocks in `src/components/ui/`
  (`Button`, `Sheet`, `Loading`/`ErrorState`/`EmptyState`), route files in `src/routes/` only wire them up.
  Employee screens get the company from `useEmployee()`; component tests use `renderScreen` and `mockApi` from `src/test/render.tsx`.
  Manager screens live in `src/features/manager/` under `/kierownik` and get the company from `useManager()`
  (tests wrap them in `AsManager` from `features/manager/test-utils.tsx`).
- Removing keeps schedule history: where the database blocks a delete (`RESTRICT`), hide instead. `EmployeeProfile.removed_at`
  (always with `is_active=False`; set by `apps/staffing/removal.py`, a removed plain employee gets 404 from `tenant_context`;
  a person with several locations only leaves the one they are removed from, `removal.leave_location`)
  and `Position.removed_at` (read live positions with `removed_at__isnull=True`). Locations with history are archived.
- Schedules are arranged only when the manager asks (after the availability deadline or once everyone has answered);
  never add jobs that generate schedules on a timer or by themselves.
- To see "Mój grafik" on demo data: publish from "Grafik" in the manager panel, or `generate_schedule --period <id> --publish`.
- Schedule edits go through `apps/scheduling/editing.py` (only the newest draft is editable, past days included; a change that adds a hard violation is refused unless the manager sends `force`, which saves it as `Assignment.forced` + pinned and the validator reports those problems as `waived`, never blocking; codes in `MANAGER_MAY_BREAK` only become warnings; publishing records `AssignmentEvent` history). Hard rules bind the generator, not the manager; only the position and pins cannot be forced.
  A person put on a shift while they have another one at the same time (here, or another location's draft or published
  schedule) is a clash: it cannot be forced, but `check` lists `clashes`, the screen asks, and `remove_clashes: true`
  takes them off the other one (with `force` too when `can_force_if_removed`). Shift explanations come from `engine/explain.py` (one validator run per candidate).
- Staffing of one date (the calendar in location settings, and "Dodaj miejsce" / "Usuń miejsce" in the schedule editor)
  is written only through `apps/staffing/day_staffing.py`: a `StaffingException` row exists only while the date differs
  from its weekday. Seats of a draft change in `editing.add_seat` / `remove_seat` (place numbers stay 1…n).
- Given-away shifts: `apps/marketplace/services.py`. The only changes to a published version in place are an approved
  handover (checked by the validator, pinned, `AssignmentEvent` reason `offer`), the manager's own change there
  (`manager_reassign` / `manager_swap`: the validator's objections are shown but the manager may overrule them with
  `force`; a forced change is not pinned; shifts that have started can be corrected too) and taking a person off a
  published shift of another location after the manager confirmed a clash (`editing.take_off_published`, reason
  `manual`). In-app notifications are written with
  `apps.notifications.services.notify`; their Polish text is built on read in `notification_text` (add a case per kind).
- Other hours of a published shift (overtime, leaving early): `apps/worktime` (`HoursChange`, keyed by period +
  `slot_key` + employee like `AssignmentEvent`). The published shift keeps its planned hours (generator, validator,
  scores); counting hours (reports, CSV, "Mój grafik", the assistant) goes through `worktime.services.worked_hours`.
  Employees report (`report`, at most 14 days back), managers decide (`decide`) or set hours at once (`set_hours`);
  every check lives in `check_report` / `check_set` / `check_approve`, which the assistant reuses before proposing.
  The assistant only prepares: an employee sends a prepared report with "Wyślij kierownikowi" (`request_id`), a
  manager's hours plan applies on "Zatwierdź zmiany" and does not need an open rule set. A person who loses a shift
  loses its other hours for good (`expired`, never revived), so no time counts twice; gaining a shift that approved
  hours run into is a problem in `check_assignment` and expires them when forced (`person_got_shift`).
- Pay ("Mój grafik", "Godziny", CSV; gross, never called an estimate): `apps/pay` (`services.PayRules` + `Pay`), the
  hours from `worked_hours` times the shift's rate on `Shift.date`, plus `PaySupplement`s for the part of the shift
  inside their hours. Rates are steps from a day (`PositionRate`, `PersonalRate`; `valid_from` null = from the start),
  so a change never moves earlier months; a person's step without an amount means the position's rate again.
  Supplement changes split the row at `change_from`. Hours without a rate are `unpriced_hours`, never 0 zł, get no
  supplement, and `pay` is null when nothing had a rate (screens then show no pay). Only the location's managers see
  rate settings (position rates in "Stanowiska i stawki", one "Zmień" per position opens name, rate and removal;
  supplements in "Dodatki do stawek" right under it); a person's own rate and pay per shift are in `MyShiftOut` (`hourly_rate`, `pay`; not on the screen).
  The generator, validator and scores never read them. Since 23.11.2026 the assistant reads pay, rates and
  supplements to work out earnings (`assistant/tools.DROPPED_KEYS` drops only phone and bank account numbers and
  screen fields).
- Assistant (a language model): only `apps/assistant/llm.py` calls the API, always from a worker job, never in a request.
  On OpenRouter the structured answer is a call of the `final_answer` tool (never `response_format` next to tools:
  providers then force JSON on every round and no tool gets called); on Anthropic it is `output_config.format`.
  Its main power is unchanged: a manager's command becomes a proposal (`apps/assistant/services.py` checks names
  against the location's data and builds action descriptions itself), an employee's message becomes preferences. Beyond
  that it answers anything about Grafikomat and the location, reading data only through `apps/assistant/tools.py`:
  existing `GET /api/...` endpoints run as the person who wrote (same permissions as the app, phones stripped). Never
  give it write tools; it says where in the app to do things. Off-topic messages get application-owned copy; mixed
  messages are answered and their preferences saved. When unsure (day, person, shift, how much) the employee's
  assistant asks one question (`EmployeeReply.question`, or the app's own about a namesake, an unknown person or
  shift, or a reading below `ASSISTANT_MIN_CONFIDENCE`; saved as `TextRequest.question` on an `answered` row, nothing
  saved); it waits while it is among the last `MAX_CONVERSATION` messages, a later message names it by number
  (`answers_question`, `TextRequest.answer_to`); it may ask again about an answer (a plain "tak" to "Czy dobrze rozumiem…" settles a doubt, `services.confirmed`), up to `services.MAX_QUESTIONS` (3)
  in a row (`services.exchange`), and then the request goes to the manager. Without a key (`llm.is_enabled()`) requests go uninterpreted. Tests
  replace `llm.read_request` / `llm.plan_command` (no real key). Importance is always a place on a list, never a level
  the manager picks; manager instructions about people are `engine.problem.Request(by_manager=True)`.
  `apps/assistant/context.py` supplies bounded history for corrections. Both structured outputs require a
  topic classification (`app|unrelated`; `unrelated` only for things clearly not about work: holidays in Poland
  (`apps/core/holidays.py`, a context line) and labour-law basics are `app`). A correction may supersede one earlier request in the same employee/scope,
  atomically and only against an unchanged snapshot. `answered` and `superseded` requests never reach the solver; extra
  preferences of one message live in `interpretation["more"]`. An invalid part blocks the entire manager plan;
  informational replies are not misses. Limits on writing to the assistant are off by default (0 = no limit):
  `ASSISTANT_COMMANDS_MONTHLY_LIMIT`, `TEXT_REQUESTS_PER_PERIOD`, `ASSISTANT_MESSAGES_PER_DAY`; when set, the request
  limit per period counts only `new`/`interpreted`/`needs_manager`.
  The chat UI slides in from the right (`components/ui/drawer.tsx`) and is one tap away on every screen after login
  (`components/assistant/AssistantFab.tsx` in the corner; on an employee's phone the last tab of the bottom bar).
  Managers: one `AssistantDrawerProvider` in the panel layout, `useAssistantDrawer().openChat({ locationId?, periodId?, text? })`;
  the chat is about the location on screen (`useChatLocation`), else the last one, else it asks which. Employees:
  `EmployeeChatProvider` in the employee layout, `useEmployeeChat().openChat(scope?)`; "Kiedy mogę" sets the month
  (`useScreenChatScope`), else the requested period or this month. Approved results live in a separate editable window:
  `AssistantRulesTable` ("Ustalenia") for managers, the saved list in `RequestsSection` for employees. Never show a
  chat inline in a page. Layouts that show the corner button leave room for it at the bottom.
  Employee requests may be lasting (`TextRequest.lasting`, Piotr 22.11.2026): they count in later periods
  (`TextRequest.lasting_from`, part of `for_periods`) until ended from a period or month (`ends_from`); only their
  undated parts with `lasting` carry over, they never move to another chat, and a correction from a later month ends
  the old one instead of superseding it.
  Agreements belong to one availability period (`apps/assistant/agreements.py`): a new period starts empty and the
  manager copies chosen ones from the previous period (`copy_from_previous`); nothing carries over by itself. An
  employee may forward a rejected message to the manager (`unread_reason="rejected"`); it is never scored.
  Costs (Piotr 22.11.2026): every model call in `services` runs inside `with llm.tracking(usage)` and is saved by
  `costs.record` as one `AssistantUsage` row (company, location, person, kind, tokens, dollars from OpenRouter's
  `usage.cost`; Claude gives no price), also when the answer failed. Only the superadmin sees them (admin
  "Koszty asystenta" → "Zestawienie miesiąca", `assistant_costs`); never put them in an endpoint or an assistant tool.
  Schedule arranging calls no API: the summary counts it as runs and solver minutes from `GenerationRun`.
- Tests: `backend/tests/` (pytest + pytest-django, real Postgres), frontend tests next to components (`*.test.tsx`, Vitest).
